# Feature Planner — 기능 기획 자동화

## 전제 조건

- `docs/features/{name}/spec-original.md`가 존재해야 한다
- `CLAUDE.md`가 프로젝트 루트에 존재해야 한다
- `--repo` 인자가 있으면 gh CLI 인증이 되어 있어야 한다

## 인자 파싱

호출: `/feature-planner {feature-name} --repo {owner/repo}`

- `{feature-name}`: 필수. `docs/features/{feature-name}/` 경로로 사용
- `--repo`: 선택. 지정 시 GitHub 이슈 등록. 미지정 시 파일 생성만 수행

---

## Step 1: 코드베이스 분석

1. `CLAUDE.md`를 읽어 기존 패턴과 컨벤션을 파악한다
2. `src/` 하위 모든 `.ts`, `.tsx` 파일을 읽어 아래를 파악한다:
   - 컴포넌트 트리 구조 (부모-자식 관계)
   - 상태 관리 패턴 (로컬 state, Context, 커스텀 훅)
   - API 레이어 구조 (함수 시그니처, 에러 처리 패턴)
   - 타입 정의 (인터페이스, 타입 별칭)
   - 네이밍 규칙 (파일, 컴포넌트, 함수, props)
3. 이 정보를 이후 단계에서 내부 컨텍스트로 사용한다 (별도 파일 생성 없음)

---

## Step 2: 스펙 셀프 검증

`docs/features/{name}/spec-original.md`를 읽고 아래 체크리스트로 검증한다.

### 검증 체크리스트

| #   | 항목                | 검증 기준                                                         |
| --- | ------------------- | ----------------------------------------------------------------- |
| 1   | CRUD 완전성         | 이 기능이 다루는 모든 생성/읽기/수정/삭제 동작이 명시되어 있는가? |
| 2   | 엣지 케이스         | 빈값, 최대값, 중복, 경계값, 에러 상황이 정의되어 있는가?          |
| 3   | UI 트리거-결과 매핑 | 모든 UI 동작이 "X하면 Y한다" 형태로 1:1 매핑되어 있는가?          |
| 4   | 구체성              | "적절히", "필요시", "등", "기타" 같은 모호한 표현이 없는가?       |
| 5   | 데이터 호환성       | 기존 데이터와의 호환성, 마이그레이션 방법이 명시되어 있는가?      |
| 6   | 제약 수치화         | 허용값, 최대치, 유효성 규칙이 구체적인 수치로 정의되어 있는가?    |

### 검증 절차

1. 각 항목을 PASS / FAIL로 판정한다
2. FAIL 항목은 AI가 스스로 보완한다:
   - Step 1의 코드 분석 결과를 근거로 기존 패턴에 맞게 결정
   - 판단이 불가능한 경우 가장 보수적인(제한적인) 선택을 한다
   - 보완한 내용에는 `<!-- AI 보완: {근거} -->` 주석을 남긴다
3. 결과를 `docs/features/{name}/spec-fixed.md`로 저장한다
4. 검증 결과 요약을 사용자에게 출력한다:
   ```
   스펙 검증 완료: 4/6 PASS, 2건 AI 보완
   - #2 엣지 케이스: 빈값 처리 추가 (기존 패턴 참고: NoteEditor의 title 빈값 체크)
   - #4 구체성: "적절히 표시" → "최대 3줄, line-clamp-3으로 표시"
   ```

---

## Step 3: 아키텍처 설계 + 자동 선택

### 설계

Step 1의 코드 분석 + Step 2의 확정 스펙을 기반으로 **2~3가지 아키텍처 안**을 설계한다.

각 안에 포함할 내용:

- 컴포넌트 트리 변경 (ASCII 다이어그램)
- 상태 관리 전략 (어디에 무슨 state를 둘 것인가)
- 데이터 흐름 (props, context, 파생 데이터)
- 신규/변경 파일 목록

### 자동 선택 — 가중치 점수 평가

각 안을 아래 4가지 기준으로 1~5점 평가한다.

| 기준                 | 가중치 | 평가 방법                                                                  |
| -------------------- | ------ | -------------------------------------------------------------------------- |
| 기존 패턴 일관성     | 40%    | CLAUDE.md의 상태 관리 패턴, 네이밍 규칙, 컴포넌트 구조와 얼마나 일치하는가 |
| 변경 범위 최소화     | 30%    | 수정 파일 수, 기존 인터페이스(props, context type) 변경 여부               |
| 테스트 용이성        | 20%    | 로직을 순수 함수로 분리 가능한가, 컴포넌트를 단독 테스트 가능한가          |
| 프로젝트 규모 적합성 | 10%    | 현재 프로젝트 규모에 과잉 설계가 아닌가                                    |

**점수 산출**: `총점 = (일관성 × 0.4) + (최소변경 × 0.3) + (테스트 × 0.2) + (적합성 × 0.1)`

가장 높은 점수의 안을 선택한다. 동점이면 "기존 패턴 일관성" 점수가 높은 안을 선택한다.

### 출력 형식

비교표와 선택 근거를 아래 형태로 정리한다 (PRD에 포함):

```markdown
| 기준                       | 안 A    | 안 B    | 안 C    |
| -------------------------- | ------- | ------- | ------- |
| 기존 패턴 일관성 (40%)     | 5       | 3       | 4       |
| 변경 범위 최소화 (30%)     | 4       | 4       | 3       |
| 테스트 용이성 (20%)        | 3       | 4       | 5       |
| 프로젝트 규모 적합성 (10%) | 5       | 4       | 3       |
| **총점**                   | **4.3** | **3.6** | **3.9** |

→ **안 A 선택**: 기존 2계층 패턴과 가장 일관되며 변경 범위가 최소
```

## Step 4: PRD 생성

Step 2 스펙 + Step 3 아키텍처를 조합하여 `docs/features/{name}/prd.md`를 생성한다.

### PRD 구조

```markdown
# {기능명} PRD

## 1. 개요

{spec-fixed.md의 개요}

## 2. 핵심 동작

{spec-fixed.md의 동작 설명}

## 3. 제약 사항

{spec-fixed.md의 제약 사항 — 표 형태}

## 4. UX 결정 사항

{spec-fixed.md의 UX 결정 — 표 형태}

## 5. Out of Scope

{spec-fixed.md에서 명시적으로 제외된 항목 + 스펙에 없지만 관련될 수 있는 기능}

## 6. 아키텍처

### 6.1 설계 원칙

### 6.2 컴포넌트 트리

### 6.3 데이터 구조

### 6.4 API 레이어

### 6.5 상태 관리

### 6.6 신규 컴포넌트

### 6.7 기존 컴포넌트 변경

### 6.8 아키텍처 선택 근거 ← 비교표 + 점수

## 7. 변경 파일 목록

{파일 — 작업 내용 표}

## 8. 구현 순서

{데이터 → UI → 상태 → 통합 순}
```

## Step 5: 이슈 분해 + GitHub 등록

### 수직 슬라이싱 원칙

각 이슈는 **데이터 → 상태 → UI를 관통하는 독립 배포 가능한 단위**로 분해한다.

- 하나의 이슈 완료 시 사용자에게 보이는 동작이 추가되어야 한다
- "타입만 추가", "컴포넌트만 생성" 같은 수평 슬라이스는 만들지 않는다

### 이슈 형식

```markdown
## Issue #{n}: {사용자 관점의 제목}

**Labels**: `feat/{name}`, `vertical-slice`

### 설명

{무엇을 왜 하는지}

### 작업 범위

{변경할 파일과 작업 내용}

### 완료 조건 (Acceptance Criteria)

- [ ] {검증 가능한 "~하면 ~한다" 형태}

### 의존성

{선행 이슈 번호 또는 "없음"}
```

### AC 테스트 가능성 셀프 검증

이슈 작성 후 아래를 검증한다:

| #   | 검증 항목                                                         |
| --- | ----------------------------------------------------------------- |
| 1   | 모든 AC가 "~하면 ~한다" 형태의 검증 가능한 문장인가?              |
| 2   | 유효성 검증 시점(입력 중 / Enter 시 / blur 시)이 명시되어 있는가? |
| 3   | 이슈 간 AC가 겹치지 않는가?                                       |
| 4   | 각 이슈가 단독으로 테스트 가능한가? (선행 이슈 완료 전제 하에)    |

검증 실패 시 해당 AC를 수정한 뒤 진행한다.

### 파일 생성

`docs/features/{name}/issues.md`에 모든 이슈를 저장한다.
맨 하단에 의존성 그래프를 ASCII로 포함한다.

### GitHub 등록 (`--repo` 지정 시만)

1. `feat/{name}`, `vertical-slice` 라벨이 없으면 `gh label create`로 생성
2. 각 이슈를 `gh issue create`로 등록
3. 등록 완료 후 이슈 URL 목록을 사용자에게 출력

모든 단계 완료 후 아래 형태로 요약을 출력한다:

```
✅ Feature Planner 완료: {feature-name}

📋 스펙 검증: {n}/6 PASS, {m}건 AI 보완
🏗️ 아키텍처: {선택된 안 이름} (총점 {점수})
📄 생성된 파일:
   - docs/features/{name}/spec-fixed.md
   - docs/features/{name}/prd.md
   - docs/features/{name}/issues.md
🎫 GitHub 이슈: {n}개 등록 ({owner/repo})
   - #1: {제목} — {URL}
   - #2: {제목} — {URL}
   ...
```
