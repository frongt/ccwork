# tdd-red

`test-scenarios`로 승인된 시나리오를 **실패하는 테스트 코드**로 바꾼다. TDD의 Red 단계다.

테스트가 먼저 실패하는 것을 눈으로 확인해야 하는 이유는 두 가지다. 테스트가 실제로 동작을 검증하는지(구현 없이도 통과하는 빈 테스트가 아닌지) 알 수 있고, 다음 단계(Green)에서 "이 테스트를 통과시키는 최소 구현"이라는 명확한 목표가 생긴다. 그래서 이 단계에서는 구현 코드를 쓰지 않는다. 구현을 슬쩍 만들어 두면 Red의 의미가 사라진다.

## 입력

- `$ARGUMENTS`: 이슈 문서 번호 `{N}` (예: `/tdd-red 1`). 시나리오 문서는 `docs/features/tag/issue-{N}.md`다.
- 다른 기능의 이슈를 쓰려면 기능 폴더명을 앞에 붙인다 (예: `/tdd-red trash 1` → `docs/features/trash/issue-1.md`). 기능명을 생략하면 `tag`다.
- 인자가 없거나, 파일이 없거나, 파일에 `## 테스트 시나리오` 섹션이 없으면 시작하지 않는다. 존재하는 `docs/features/*/issue-*.md` 목록을 보여주고 어떤 이슈인지 묻고 멈춘다. 시나리오가 없다는 것은 승인된 시나리오가 없다는 뜻이므로 `/test-scenarios`를 먼저 하도록 안내한다.

## 절대 하지 않는 것

- `src/`의 구현 코드(`*.ts`, `*.tsx` 중 `*.test.*`가 아닌 것)를 만들거나 수정하지 않는다. 빈 함수나 스텁도 만들지 않는다. 만들면 테스트가 "구현이 없어서"가 아니라 "스텁이 틀려서" 실패하게 되어 Red의 의미가 흐려진다.
- 테스트 대상 모듈이 없을 때 그 파일을 생성하지 않는다. 사용자에게 알리고 그 대상의 테스트는 쓰지 않는다 (1-1단계).
- 테스트 파일 외의 파일(`vite.config.ts`, `test-setup.ts`, `package.json` 등)을 바꾸지 않는다. 패키지가 모자라면 설치하지 말고 사용자에게 알린다.
- 실제 `db.json`(`localhost:3001`)의 기존 노트를 읽거나 수정/삭제하는 테스트를 쓰지 않는다. 수정/삭제는 테스트가 직접 만든 데이터로만 한다 ("데이터 보호" 참조).
- 테스트를 통과시키려고 테스트를 느슨하게 고치지 않는다. 시나리오가 요구하는 것을 그대로 검증한다.
- 승인된 시나리오를 추가·삭제·변경하지 않는다. 시나리오가 모호하거나 모순되면 임의로 해석하지 말고 사용자에게 묻는다.
- 커밋/푸시는 사용자가 요청할 때만 한다.

## 절차

### 1. 문서 읽기

`docs/features/{feature}/issue-{N}.md`에서 `## 시그니처`와 `## 테스트 시나리오`를 읽는다. 시그니처는 import 경로, 함수/훅 이름, Props, 반환 타입의 기준이고, 시나리오는 작성할 테스트 목록이다. 시그니처가 가리키는 기존 코드(`NotesContext`, `NoteList` 등)도 읽어 현재 동작을 파악한다. 테스트가 기존 코드의 어느 지점에서 실패할지 알아야 올바른 이유로 실패하는지 판단할 수 있다.

시나리오는 `번호. [분류] 대상 — should ... when ...` 형식이다. 대상(함수/훅/컴포넌트)별로 묶어 어느 테스트 파일에 들어갈지 정한다.

### 1-1. 대상 모듈 존재 확인

시그니처가 가리키는 대상 파일(테스트가 import할 파일)이 실제로 있는지 `Glob`/`Read`로 확인한다. 파일이 없으면:

1. **그 파일을 만들지 않는다.** 빈 파일, 빈 함수, `declare`만 있는 파일, 스텁 모두 포함한다. 구현 파일을 만드는 것은 이 스킬이 아니라 Green 단계의 일이다.
2. 해당 대상의 테스트 코드는 **쓰지 않는다.** 모듈이 없는 상태로 쓰면 import 오류로 실패하는 잘못된 Red가 되기 때문이다.
3. 어떤 파일이 없는지, 그 파일을 import해야 하는 시나리오 번호가 무엇인지 사용자에게 알린다.
4. 모듈이 있는 대상의 시나리오만 계속 진행한다. 모든 대상이 없으면 아무것도 쓰지 않고 여기서 멈춘다.

없는 모듈 목록과 건너뛴 시나리오는 최종 보고에 그대로 남겨, 사용자가 모듈을 준비한 뒤 다시 실행할 수 있게 한다.

### 2. 테스트 파일 배치

테스트 대상 파일과 **같은 디렉토리**에 `{파일명}.test.ts` / `{파일명}.test.tsx`로 둔다. 순수 함수·훅은 `.ts`, JSX를 렌더링하면 `.tsx`다.

- `src/utils/trash.ts` → `src/utils/trash.test.ts`
- `src/hooks/useConfirmAction.ts` → `src/hooks/useConfirmAction.test.ts`
- `src/components/NoteList.tsx` → `src/components/NoteList.test.tsx`
- `src/context/NotesContext.tsx` → `src/context/NotesContext.test.tsx`
- `App` 시나리오는 `src/App.test.tsx`

`describe` 블록은 함수/컴포넌트 단위 하나씩이다 (`describe('partitionNotes', () => { it('should ...') })`). 한 파일에 대상이 둘 이상이면 describe를 나란히 둔다.

### 3. 시나리오를 하나씩 작성 → 실행 → 실패 확인

시나리오 번호 순서로, **한 시나리오씩** 반복한다. 한꺼번에 다 쓰고 돌리면 어떤 테스트가 어떤 이유로 실패하는지 구분하기 어렵다.

1. 시나리오 한 줄을 `it`으로 옮긴다.
   - 테스트 이름은 시나리오의 `should ... when ...` 문장을 그대로 쓴다 (`it('should 최근 삭제 순으로 정렬해 반환 when ...', ...)`). 시나리오 번호와 추적이 되도록 이름을 바꾸지 않는다.
   - 한 `it`은 한 가지만 검증한다. 시나리오가 한 줄에 한 가지씩 쪼개져 있으니 그대로 따른다.
2. 방금 쓴 테스트만 실행한다: `npx vitest run <테스트 파일> -t "<테스트 이름의 고유한 일부>"`.
3. 결과를 확인한다.
   - **실패**: 실패 이유를 읽는다. 구현이 없거나 동작이 아직 없어서 실패하면 의도한 Red다. 다음 시나리오로 간다.
   - **통과**: 경고 신호다. Red의 목표는 작성한 테스트가 전부 실패하는 것이므로 통과를 그냥 두지 않는다.
     1. 단언이 약한지 먼저 점검한다. 약하면 시나리오가 요구하는 만큼 강화해 다시 실행한다 (예: mock 응답을 입력과 다른 값으로 만들어 "서버 응답으로 교체"와 "입력 병합"을 구분).
     2. 강화해도 통과하면 기존 코드가 이미 충족하는 시나리오다. 테스트를 억지로 실패시키거나 시나리오를 임의로 빼지 말고, 사용자에게 어느 시나리오가 어떤 기존 코드 때문에 통과하는지 알리고 선택지를 준다: (a) 회귀 테스트로 유지 (b) 이슈 테스트에서 제외하고 시나리오 문서에 표시 (c) 별도 분류.
     3. 사용자가 유지를 택하면 해당 테스트 위에 `// 회귀 테스트: 기존 {코드}가 이미 충족하는 동작이라 Red 단계에서도 통과한다.` 주석을 달고, 최종 보고에서 Red 완료 기준(전부 실패)의 예외로 따로 적는다.
        구현은 건드리지 않는다.
   - **엉뚱한 이유로 실패** (오타, 잘못된 import 경로, 셋업 오류): 테스트를 고쳐서 의도한 이유로 실패하게 만든다.

**import 오류(모듈 없음)는 올바른 Red가 아니다**: 테스트 대상 모듈이 없어서 `Failed to resolve import`로 실패하는 것은 동작을 검증하기 전에 파일이 깨진 것이라, 구현이 무엇을 해야 하는지 아무것도 알려주지 않는다. 진짜 Red는 모듈이 존재하는 상태에서 **단언이 실패**하는 것이다. 그래서 3단계를 시작하기 전에 대상 모듈이 있는지부터 확인한다 (아래 "대상 모듈 존재 확인").

### 테스트 작성 원칙: 사용자가 보는 방식

컴포넌트·조립(App) 테스트는 구현 세부가 아니라 **화면에서 보이는 것과 사용자가 하는 행동**을 검증한다. 이렇게 쓰면 이후 Refactor 단계에서 내부 구조를 바꿔도 테스트가 깨지지 않는다.

- 요소는 `getByRole` / `getByLabelText` / `getByText`로 찾는다 (예: `getByRole('button', { name: '삭제' })`, `getByLabelText('휴지통')`). `data-testid`나 CSS 클래스, 컴포넌트 내부 상태는 쓰지 않는다.
- 행동은 `@testing-library/user-event`(`userEvent.setup()` + `await user.click(...)`)로 한다. 이 프로젝트에 설치되어 있다.
- 결과는 화면으로 확인한다: `expect(screen.getByRole('alertdialog')).toBeInTheDocument()`, `queryBy...`로 사라짐 확인, 비동기 갱신은 `findBy...`/`waitFor`.
- 순수 함수(`utils/*`)는 입력과 반환값으로, 훅은 `renderHook` + `act`로 검증한다. 렌더링이 필요 없는 규칙을 컴포넌트로 감싸 테스트하지 않는다.

### 테스트를 결정적으로 만들기 (입력 고정)

같은 코드가 실행 시점이나 환경에 따라 다른 결과를 내면, 테스트가 어떤 날은 통과하고 어떤 날은 실패한다(flaky). 그러면 Red에서 "구현이 없어서 실패"인지 "오늘 시간 때문에 실패"인지 구분할 수 없고, Green 이후에도 믿을 수 없는 테스트가 된다. 결과가 입력 외의 값에 좌우되면 그 값을 **stub으로 고정**해서 기대 결과를 하나로 만든다.

- **시간/날짜**: `new Date()`, `Date.now()`에 따라 값이 달라지면(예: `deletedAt`에 기록되는 현재 일시, "오전/오후" 같은 분기) 시계를 고정한다.
  - `vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime(new Date('2025-01-15T09:00:00.000Z'))`로 **`Date`만** 고정한다. 타이머 전체를 가짜로 만들면 `userEvent`와 `waitFor`가 멈추므로 `toFake: ['Date']`로 제한한다.
  - `afterEach`에서 `vi.useRealTimers()`로 되돌려 다른 테스트에 새지 않게 한다.
  - 같은 함수의 결과가 시각에 따라 갈리면(아침/저녁, 오전/오후) 분기마다 시각을 달리 고정한 테스트를 각각 둔다. 단, 시나리오에 있는 것만 쓴다.
  - "현재 일시가 기록된다"는 시나리오는 고정한 시각의 ISO 문자열(`'2025-01-15T09:00:00.000Z'`)이 요청 본문에 들어갔는지로 단언한다.
- **로케일/타임존**: `toLocaleDateString('ko-KR')`는 실행 환경의 타임존에 따라 날짜가 하루 어긋날 수 있다. 날짜 경계에서 먼 시각(정오 무렵 UTC)을 쓰고, 기대값은 같은 함수(`new Date(iso).toLocaleDateString('ko-KR')`)로 계산한다.
- **그 밖의 비결정 값**: `Math.random`, `crypto.randomUUID`, 서버가 생성하는 `id` 등도 `vi.spyOn`으로 고정하거나 mock 응답에 고정값을 넣는다.
- 시간 stub은 **테스트 파일 안에서** 설정한다. `vite.config.ts`나 `test-setup.ts`는 바꾸지 않는다.

### 데이터 보호: 실제 db.json을 건드리지 않기

`db.json`은 json-server가 런타임에 직접 수정하는 실제 데이터다. 수정·삭제 테스트가 기존 노트를 건드리면 사용자의 데이터가 사라지거나 바뀌고, git diff에 데이터 변경이 남는다. 그래서 단위/컴포넌트 테스트는 **실제 서버에 절대 요청을 보내지 않는다.**

- **기본은 mock**: `vi.mock('../api/notes')`로 `api` 모듈을 통째로 대체하고, 이 파일 안에서 만든 **테스트 전용 데이터**를 반환하게 한다 (`fetchNotes`가 `[note-a, note-b]`를 돌려주는 식). `fetch` 전역을 stub(`vi.stubGlobal('fetch', vi.fn())`)해 응답을 고정하는 방법도 쓸 수 있다. 어느 쪽이든 `localhost:3001`로 나가는 요청이 없어야 한다.
- **수정/삭제 테스트는 "먼저 데이터를 만들고 → 그 데이터를 수정/삭제"하는 순서**로 쓴다 (Arrange → Act → Assert). 기존 `db.json`의 노트를 가정하지 않는다.
  - 파일 안 헬퍼(`createTestNote({ id: 'test-1', title: '테스트 노트' })`)로 노트를 만들어 mock의 초기 데이터로 넣고, 그 노트에 대해 삭제/수정을 수행한다.
  - 테스트 id는 `test-1`처럼 실제 데이터와 구분되는 값을 쓴다.
  - mock 서버가 상태를 가져야 하면(삭제 후 재조회 등) 테스트 안에서 배열을 만들어 `mockImplementation`으로 PATCH/DELETE가 그 배열만 바꾸게 한다. 실제 파일은 건드리지 않는다.
- **실제 서버를 쓰는 통합 테스트가 꼭 필요한 경우**는 시나리오가 그것을 요구할 때뿐이다. 이때는 `POST`로 테스트 노트를 먼저 만들고, 그 노트만 수정/삭제하고, `afterEach`/`afterAll`에서 만든 노트를 `DELETE`로 정리한다. 서버가 떠 있어야 하므로 시작 전에 사용자에게 알리고, 기존 노트의 id를 하드코딩하지 않는다. 이 경우에도 정리 후 `git diff db.json`에 변경이 없는지 확인해 보고한다.
- 테스트 실행 전후에 `git status`의 `db.json`이 이 스킬 때문에 바뀌지 않았는지 확인한다. 이미 수정되어 있던 `db.json`(작업 중 변경)은 건드리지 않고 그대로 둔다.

### 그 밖의 격리

- 컴포넌트 테스트: `useNotes`를 mock하거나, 실제 `NotesProvider`로 감싸고 `api/notes`를 mock한다. Context의 상태 갱신 자체가 검증 대상이면 Provider + `api` mock, 컴포넌트만 검증하면 `useNotes` mock이 단순하다.
- `alert`는 `vi.spyOn(window, 'alert').mockImplementation(() => {})`로 가로채 호출 여부를 단언한다.
- 서버 호출 여부 단언("서버 호출 없이")은 mock 함수의 `not.toHaveBeenCalled()`로 한다.
- 테스트 간 오염을 막기 위해 `beforeEach`에서 mock을 초기화한다 (`vi.clearAllMocks()`).
- 테스트 데이터 헬퍼는 파일 안에 둔다. 파일마다 중복되더라도 이 단계에서 공용 유틸을 `src/`에 새로 만들지 않는다 (테스트 파일만 생성한다는 제약).

### 4. 전체 확인

모든 시나리오를 작성했으면 `npm test`(= `vitest run`)를 실행해 **작성한 테스트가 전부 실패**하는지 확인한다. 최종 보고에 아래를 포함한다.

- 작성한 테스트 파일 목록과 시나리오 수 (시나리오 N개 ↔ `it` N개로 누락·초과가 없는지 대조)
- 전체 결과 요약 (통과/실패 개수)
- 실패 이유: 모두 동작 미구현으로 인한 단언 실패여야 한다. import 오류로 실패한 테스트가 있으면 잘못된 Red이므로 원인을 찾아 고친다.
- 모듈이 없어 건너뛴 대상과 시나리오 번호 (1-1단계)
- 통과해 버린 테스트가 있으면 시나리오 번호와 이유
- 다음 단계 제안: Green(최소 구현으로 테스트 통과). 이 스킬에서는 구현하지 않는다.

이슈와 무관하게 이미 있던 테스트가 있으면 이슈 시나리오 테스트와 구분해서 보고한다. 기존 테스트가 실패하는 것은 이 스킬이 만든 문제가 아닐 수 있으므로 건드리지 않고 알린다.
