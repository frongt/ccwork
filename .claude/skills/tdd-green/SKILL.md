# tdd-green

`tdd-red`로 작성한 **실패하는 테스트를 통과시키는 최소한의 구현**을 쓴다. TDD의 Green 단계다.

"최소한"이 핵심이다. 테스트가 요구하는 만큼만 구현해야 코드가 테스트로 설명되고, 테스트에 없는 동작이 슬쩍 들어와 검증 없이 남는 일이 없다. 더 나은 구조나 일반화는 다음 단계(Refactor)에서 테스트가 지켜 주는 상태로 한다. 그래서 이 단계에서는 "이왕 하는 김에"를 하지 않는다.

## 입력

- `$ARGUMENTS`: 이슈 문서 번호 `{N}` (예: `/tdd-green 1`). 시나리오 문서는 `docs/features/tag/issue-{N}.md`다.
- 다른 기능은 기능 폴더명을 앞에 붙인다 (예: `/tdd-green trash 1` → `docs/features/trash/issue-1.md`). 생략하면 `tag`다.
- 인자가 없거나, 파일이 없거나, `## 테스트 시나리오` 섹션이 없으면 시작하지 않는다. 존재하는 `docs/features/*/issue-*.md` 목록을 보여주고 어떤 이슈인지 묻고 멈춘다.
- 이 이슈의 테스트 파일이 아직 없으면(Red 미완료) `/tdd-red {N}`을 먼저 하도록 안내하고 멈춘다.

## 절대 하지 않는 것

- **테스트 파일(`*.test.ts`, `*.test.tsx`)을 수정하지 않는다.** 테스트가 틀려 보여도 고치지 않는다. 통과시키려고 테스트를 고치면 Red에서 확인한 "요구사항"이 사라진다. 테스트가 시나리오와 어긋났거나 모순이면 구현을 억지로 맞추지 말고 개발자에게 보고하고 멈춘다.
- 없는 모듈의 stub(빈 시그니처)을 직접 만들지 않는다. 2단계에서 `/tdd-signature`를 안내하고 멈춘다.
- 테스트에 없는 기능, 옵션, 분기, 방어 코드를 구현하지 않는다.
- 불필요한 추상화를 만들지 않는다. 한 곳에서만 쓰는 헬퍼, 설정 객체, 범용 래퍼를 미리 만들지 않는다. 단, CLAUDE.md의 **분리 원칙**(규칙은 `utils`, 상태·동작이 둘 이상이면 `hooks`, 표현은 순수 컴포넌트)이 시그니처 문서에 이미 구조로 정해져 있으면 그 구조를 따른다. 이것은 추상화를 더하는 것이 아니라 확정된 설계를 지키는 것이다.
- 디자인 시스템 문서에 없는 시각적 요소(색, 아이콘, 그림자, 애니메이션 등)를 임의로 추가하지 않는다.
- 시나리오 문서의 체크박스 외에는 문서를 고치지 않는다. 시나리오를 추가·삭제·변경하지 않는다.
- 커버리지를 올리려고 테스트를 추가하지 않는다 (8단계).
- `vite.config.ts`, `package.json` 등 설정 파일을 바꾸지 않는다. 패키지가 모자라면 설치하지 말고 알린다.
- 실제 `db.json`을 바꾸지 않는다. 테스트가 mock으로 격리되어 있어야 하며, 실행 후 `git status`의 `db.json`이 이 스킬 때문에 바뀌지 않았는지 확인한다. 이미 수정되어 있던 `db.json`(작업 중 변경)은 그대로 둔다.
- 커밋/푸시는 사용자가 요청할 때만 한다.

## 절차

### 1. 실패 테스트 확인

`npm test`를 실행해 실패하는 테스트 목록(파일, 테스트 이름, 실패 이유)을 파악한다. 이 이슈의 테스트와 이슈와 무관하게 이미 실패하던 테스트를 구분해 둔다. 후자는 이 스킬이 만든 문제가 아닐 수 있으므로 건드리지 않고 마지막 보고에서만 알린다.

### 2. collect 실패 감지

테스트 파일이 import하는 모듈이 없으면 vitest는 그 파일을 **수집(collect)하지 못하고** 파일 전체를 실패 1건으로 센다. 이 경우 파일 안의 테스트가 보고되지 않아 실제 실패 목록이 줄어들어 보인다. 이를 잡기 위해 건수를 대조한다.

1. 시나리오 문서 `## 테스트 시나리오`의 체크박스(`- [ ]`, `- [x]` 모두) **총 건수**를 센다.
2. vitest가 보고한 `Tests` 총 수(통과 + 실패 + 건너뜀)와 비교한다. 이슈와 무관한 기존 테스트가 섞여 있으면 이 이슈의 테스트 파일만 대상으로 `npx vitest run <파일>`로 센다.
3. **일치**하면 다음 단계로 간다.
4. **불일치**하면 import 대상 모듈이 없는 것이다. `Failed to resolve import`나 `Cannot find module` 오류로 어떤 파일이 없는지 찾는다. **stub을 직접 만들지 않고 멈춘다.** 빈 시그니처 생성은 `tdd-signature`의 몫이고, Green에서 stub을 만들면 두 스킬의 규칙이 어긋날 수 있기 때문이다.
   - 없는 모듈의 파일 경로와, 그 모듈을 import하는 테스트 파일을 개발자에게 알린다.
   - `/tdd-signature {N}`(같은 기능 폴더 인자 포함)을 먼저 실행하도록 안내하고 멈춘다. 실행 후 `/tdd-green {N}`을 다시 하면 된다.
   - 모듈은 다 있는데 건수가 어긋나면(시나리오와 `it` 개수가 다름) 임의로 맞추지 말고 개발자에게 보고하고 멈춘다.

### 3. 디자인 컨텍스트 로드

구현 대상에 **UI 컴포넌트(`.tsx`의 JSX, 스타일 클래스)**가 있을 때만 한다. 순수 함수·훅·Context·API만 구현하는 이슈면 이 단계를 건너뛴다. 스타일 없는 코드를 위해 디자인 문서를 읽는 것은 낭비다.

1. `docs/design-system/README.md`를 읽는다. 구현 대상 컴포넌트의 시각적 스펙(색상, 간격, 레이아웃, 상태별 표현)을 파악하고, README가 가리키는 하위 문서(`foundations`, `components`, `rules/do-and-dont.md` 등) 중 구현 대상에 필요한 것만 추가로 읽는다. 대상 컴포넌트에 해당하는 문서가 README에 연결되어 있지 않으면 `docs/design-system/` 아래를 `Glob`/`Grep`으로 찾아 해결한다 (`design-system` 스킬이 문서를 골라 읽는 방식과 같다).
2. `docs/features/{feature}/issue-{N}.md`에 **`디자인 참고` 섹션**이 있으면 함께 읽는다. 이 이슈에 한정된 시각 요구가 거기 있다.
3. `CLAUDE.md`의 스타일링 컨벤션(Tailwind v4 유틸리티 클래스, 시맨틱 색상 토큰, `cursor-pointer` / `hover:opacity-75`, 한국어 UI 문구)과 Do / Don't를 따른다.
4. `docs/design-system/`이 없으면 이 단계를 건너뛰고 CLAUDE.md 컨벤션만 따른다.

디자인 문서와 CLAUDE.md의 컨벤션이 충돌하면 디자인 문서의 Do / Don't를 우선하되, 충돌 사실을 최종 보고에 적는다.

### 4. 첫 번째 실패 테스트를 통과시키는 최소 코드

실패하는 테스트를 **하나씩** 다룬다. 시나리오 번호 순서를 따른다. 한꺼번에 여러 테스트를 겨냥해 쓰면 어떤 코드가 어떤 테스트를 위한 것인지 흐려지고 "최소"가 깨진다.

1. 대상 테스트를 읽고 **무엇을 단언하는지**를 정확히 파악한다. 테스트가 요구하는 것만 구현한다.
2. 구현 파일을 수정한다. `tdd-signature`가 만든 stub이었다면 `throw new Error('not implemented')`를 지우고 `_` 접두어 파라미터와 `_props`를 CLAUDE.md 컨벤션(구조 분해, 정상 이름)으로 되돌린다. 이때 `eslint-disable-next-line` 주석도 함께 제거한다.
3. **UI 컴포넌트**는 테스트가 요구하는 동작을 충족하면서 3단계에서 파악한 스타일 스펙을 함께 적용한다.
   - 디자인 시스템 문서에 **명시된** Tailwind 클래스, 레이아웃 구조, 상태별 표현을 그대로 쓴다. 비슷하게 흉내 내지 않고 문서의 클래스를 가져온다.
   - 문서에 없는 시각 요소는 넣지 않는다. 스펙이 비어 있는 부분은 비워 두고(또는 CLAUDE.md 컨벤션의 기본 패턴만 쓰고) 보고에 "스펙 없음"으로 적는다.
   - 스타일은 테스트가 검증하지 않으므로 통과 여부와 무관해 보이지만, 이후 마이그레이션 비용을 줄이려고 처음부터 맞추는 것이다. 스타일 때문에 테스트 통과가 늦어지면 안 된다. 테스트가 먼저다.
4. **컴포넌트 규칙**(CLAUDE.md): 함수형 + named export, 파일명 = export명, `XxxProps`는 컴포넌트 바로 위, 조건부 렌더링은 early return, JSX 구획은 `{/* 제목 */}` 한국어 주석, `useNotes()`는 최상위 조립 컴포넌트에서만, UI 문구는 한국어, 모든 입력 요소에 `aria-label`. 서버 호출은 컴포넌트가 아니라 Context 경유, API는 `api/*.ts`에서 `!res.ok` 시 `throw new Error('Failed to ...')`.

### 5. 통과 확인 + 회귀 확인 (피드백 루프)

1. 방금 겨냥한 테스트를 실행한다: `npx vitest run <테스트 파일> -t "<테스트 이름의 고유한 일부>"`.
2. 통과하면 `npm test`로 **전체 테스트**를 실행해 이전에 통과하던 테스트가 깨지지 않았는지(회귀) 확인한다.
3. 아직 실패하면 에러 메시지를 읽고 **원인을 분석**한 뒤 코드를 고치고 1번부터 다시 한다. 감으로 바꾸지 않는다. 실패 메시지가 가리키는 지점(기대값 vs 실제값, 호출되지 않은 mock, 못 찾은 요소)에서 출발한다.
4. 반복은 **최대 5회**다. 5회 안에 통과하지 않으면 중단하고 개발자에게 보고한다. 보고에는 테스트 이름, 마지막 에러 메시지, 시도한 수정들, 의심되는 원인(테스트가 시나리오와 어긋났는지, 구현 쪽 문제인지)을 담는다. 5회를 넘겨 계속 시도하거나, 막혔다고 테스트를 고치지 않는다. 같은 방식으로 반복해서 안 되면 접근이 틀린 것이므로 사람의 판단이 필요하다.
5. 회귀가 생겼다면 방금 변경이 원인이다. 방금 변경을 고쳐 회귀를 없앤다. 기존 테스트를 고치지 않는다.

### 6. 시나리오 체크

해당 테스트가 통과하고 회귀가 없으면 `docs/features/{feature}/issue-{N}.md`의 대응하는 항목을 `- [ ]` → `- [x]`로 바꾼다. 시나리오 번호와 테스트 이름(`should ... when ...`)으로 대응시킨다. 체크 외에 문서의 다른 부분은 바꾸지 않는다.

### 7. 다음 실패 테스트로 반복

아직 실패하는 이슈 테스트가 남아 있으면 4단계로 돌아간다. 모두 통과할 때까지 반복한다. 이전 테스트를 위해 쓴 코드가 다음 테스트의 요구와 부딪히면 둘 다 만족하도록 최소로 고친다.

### 8. 커버리지 측정 (참고용)

이슈의 테스트가 전부 통과하고 `npm test`가 전체 통과이면 `npx vitest run --coverage`(또는 `npm run test:coverage`)를 실행한다. 이 프로젝트에는 `@vitest/coverage-v8`과 `vite.config.ts`의 `test.coverage` 설정이 이미 있다. 없으면 설치·설정하지 말고 알린다.

- 이슈 구현 파일의 **미커버 라인**을 확인하고, 각각이 **시나리오에서 빠진 케이스**인지 불필요한 코드인지 판단해 개발자에게 보고한다.
- **커버리지를 올리기 위한 테스트를 추가하지 않는다.** 이 숫자는 시나리오가 충분했는지 돌아보는 참고용이다. 테스트가 없는 줄을 보고 테스트를 더하면 시나리오 승인 과정이 우회된다. 빠진 케이스는 보고만 하고, 시나리오 보강은 개발자가 `/test-scenarios`로 결정한다.
- 미커버 라인이 "테스트에 없는데 내가 넣은 코드"라면 4단계의 "테스트에 없는 기능 금지"를 어긴 것이다. 그 코드는 지운다 (지운 뒤 `npm test`로 다시 확인한다).
- `coverage/` 폴더는 `.gitignore` 대상이다. 커밋 대상에 포함시키지 않는다.

### 9. 결과 요약

아래를 보고한다.

- **구현/수정한 파일** 목록 (stub이던 것을 구현한 파일과 기존 코드를 수정한 파일을 구분)
- **테스트 결과**: 이슈 테스트 통과/전체, 전체 `npm test` 결과, 회귀 여부
- **체크한 시나리오**: `[x]` 처리한 항목 수 / 전체 (건수가 맞는지)
- **collect 실패 감지** 결과: 시나리오 수와 Tests 수 일치 여부 (불일치로 멈췄다면 없는 모듈 목록)
- **디자인 적용**: 참고한 문서, 적용한 스타일, 스펙이 없어 비워 둔 부분, 문서와 CLAUDE.md의 충돌
