# test-scenarios

이슈 하나를 **시그니처 확정 → 테스트 시나리오 도출** 순서로 처리한다. 결과는 이후 TDD(Red → Green → Refactor)에서 테스트 코드를 쓸 때의 설계도가 된다.

시그니처를 먼저 못 박는 이유는 시나리오의 기준점이 필요해서다. 이름과 타입, 에러 조건이 정해져야 "무엇을 어떻게 검증할지"를 구체적으로 쓸 수 있고, TDD에서 테스트를 먼저 쓸 때 인터페이스가 흔들리지 않는다.

## 입력

- `$ARGUMENTS`: **이슈 문서 번호** `{N}`(예: `/test-scenarios 1`). `issues.md`의 "이슈 요약" 표 번호이자 GitHub 이슈 제목의 `Tag [N]`이다. 산출물 파일명 `issue-{N}.md`도 이 번호를 쓴다.
- 문서 번호 `{N}`과 GitHub 이슈 번호 `{G}`는 다르다. GitHub는 PR과 번호를 공유해서 `Tag [1]`이 `#2`처럼 밀려 있을 수 있다. 인자를 GitHub 번호로 해석하지 않는다.
- GitHub 이슈 찾기: `gh issue list --state all --limit 100 --json number,title`로 목록을 받아 제목이 `Tag [{N}] `로 시작하는 이슈를 고른다. 그 이슈의 번호가 `{G}`이고, 이후 `gh issue view {G}`로 내용을 읽는다.
- 인자가 없거나, 일치하는 이슈가 없거나 둘 이상이면 시작하지 않는다. 목록을 보여주고 어떤 이슈인지 사용자에게 묻고 멈춘다.
- 이슈 본문의 `#번호`(예: "선행 이슈: #2")는 GitHub 번호다. 문서 번호가 필요하면 위 목록에서 해당 이슈의 제목의 `Tag [N]`으로 바꿔서 쓴다.
- `gh`가 PATH에 없으면 `C:\Program Files\GitHub CLI\gh.exe`를 전체 경로로 호출한다.

## 절대 하지 않는 것

- 구현 코드(함수 본문, 컴포넌트 JSX, 훅 로직)를 쓰지 않는다. 시그니처는 **선언만** 쓴다.
- 테스트 코드(`describe`/`it`/`expect`)를 쓰지 않는다. 시나리오는 문장으로만 쓴다.
- 승인받지 않고 다음 단계로 넘어가지 않는다.
- 시그니처와 시나리오 모두 **개발자 승인을 받은 뒤에만** 파일에 쓴다. 승인 전 초안을 문서에 먼저 쓰지 않는다.
- 커밋/푸시는 사용자가 요청할 때만 한다.

## 절차

### 1. 시그니처 확정

아래를 읽고 이슈가 건드리는 대상의 시그니처를 정한다.

- GitHub 이슈: `gh issue view {G}` — 설명, 관통 범위, 완료조건(AC), 의존성
- `docs/features/tag/prd.md` — 특히 ADR-001의 계층별 파일 표와 구현 순서
- 필요하면 `docs/features/tag/spec-fixed.md` — 입력 규칙, 문구, 동작 세부
- 코드베이스 — 의존하는 기존 코드. 이슈에 선행 이슈가 있으면 선행 이슈의 시그니처가 `docs/features/tag/issue-{선행 N}.md`에 있는지 확인해 그대로 따른다.

정할 것:

- **함수 시그니처**: 이름, 파라미터 이름과 타입, 반환 타입 (`utils/*.ts`의 순수 함수, API 함수, Context 함수, 훅의 반환 타입)
- **에러 케이스**: 어떤 상황에서 `Error`를 던지는지. 검증 실패처럼 던지지 않고 결과값으로 돌려주는 경우는 반환 타입으로 표현하고 에러와 구분해 적는다.
- **컴포넌트 Props 타입**: `XxxProps` 인터페이스. 콜백은 `onXxx`.

기존 패턴을 따른다. 이 프로젝트의 관례는 다음과 같다.

- `api/notes.ts`: `async` 함수, `fetch` → `!res.ok`이면 `throw new Error('Failed to ...')` → `res.json()`. `Promise<Note>` 또는 삭제처럼 `Promise<void>`.
- `NotesContext`: 서버 응답 후 로컬 상태 갱신, `XxxContextType` 인터페이스로 함수 노출, 에러는 호출한 컴포넌트가 처리.
- 컴포넌트: named export, 파일명과 export명 일치, `XxxProps`는 컴포넌트 바로 위에 정의. 규칙은 `utils`, 상태·동작이 둘 이상이면 `hooks/use*.ts`, 표현은 props만 받는 순수 컴포넌트(ADR-002).
- 선택 필드는 옵셔널(`tags?: string[]`)이고 사용처에서 `?? []`로 처리한다.

이슈가 건드리지 않는 대상(후속 이슈에서 만들 것)은 시그니처에 넣지 않는다. 이슈 범위 밖으로 번지면 범위 초과 구현의 씨앗이 된다.

### 2. 시그니처 검토/승인

확정한 시그니처를 개발자에게 코드 블록으로 보여주고, 근거가 불확실한 결정(예: 검증 실패를 throw로 할지 결과값으로 할지)은 선택지와 추천을 함께 적는다. **승인을 받을 때까지 3단계로 가지 않는다.** 수정 요청이 있으면 반영해서 다시 보여준다.

### 3. 시그니처 기록

승인된 시그니처를 `docs/features/tag/issue-{N}.md` **상단**에 쓴다. 파일이 이미 있으면 덮어쓰기 전에 내용을 확인하고 사용자에게 어떻게 할지 묻는다.

````markdown
# 이슈 {N}. {이슈 제목} — 테스트 시나리오

> GitHub 이슈: #{G} / 기준 문서: prd.md, spec-fixed.md

## 시그니처

### {파일 경로}

```ts
(선언만. 본문 없음)
```

#### 에러 케이스

- {조건} → {Error 메시지 또는 결과값}
````

### 4. 시나리오 도출

시그니처를 입력으로 시나리오를 도출한다. 구현 코드를 상정하지 말고, 선언된 인터페이스와 이슈 설명만으로 "이 계약이 지켜지는지"를 묻는 질문을 만든다.

분류:

- **정상**: 대표적인 올바른 사용
- **경계**: 한계값 직전·직후, 빈 값, 옵셔널 필드 없음(`tags` 없는 기존 노트), 첫/마지막 요소
- **예외**: 에러를 던지는 경우, 검증 실패, 실패한 서버 응답

형식(한 줄에 하나):

```
[정상/경계/예외] 함수명 — should [기대동작] when [조건]
```

예: `[경계] validateTag — should 추가를 거절하고 길이 초과 문구를 반환 when trim 후 길이가 51자인 입력`

함수명 자리에는 대상(함수, 훅, 컴포넌트)을 쓴다. 한 줄이 한 가지만 검증하게 쪼갠다. 테스트 코드는 쓰지 않는다. 이 단계의 시나리오는 파일에 쓰지 않고 대화에만 정리한다. 승인 전 내용이 문서에 남지 않게 하려는 것이다.

### 5. AC 대조

1. `gh issue view {G}`로 AC 목록을 읽는다.
2. 각 AC에 대응하는 시나리오가 최소 하나 있는지 대조한다.
3. 시나리오가 없는 AC가 있으면 시나리오를 추가한다. 새로 추가한 시나리오는 4단계와 같은 형식을 쓴다. UI 동작처럼 시그니처에 직접 드러나지 않는 AC는 해당 컴포넌트나 조립 대상을 함수명 자리에 쓴다.
4. AC 커버리지 대조표를 만든다. 이 단계도 파일에 쓰지 않고 대화에만 정리한다.

```markdown
## AC 커버리지

| AC        | 시나리오             |
| --------- | -------------------- |
| {AC 요약} | {시나리오 번호/요약} |
```

모든 AC가 최소 1개 시나리오로 커버되면 표의 "시나리오" 칸이 빈 곳이 없어야 한다. 시나리오로 만들기 어려운 AC(예: 문서 규칙)는 비워 두지 말고 이유를 적는다.

### 6. 시나리오 검토/승인

시나리오와 AC 커버리지를 개발자에게 보여주고 **승인을 받는다. 승인 전에는 파일에 쓰지 않고 다음 단계로 가지 않는다.** AC 밖에서 스킬이 덧붙인 제안이 있으면 그것도 같이 보여주고 포함 여부를 묻는다. 수정 요청이 있으면 반영해서 다시 보여준다.

### 7. 시나리오 기록

승인된 시나리오를 `docs/features/tag/issue-{N}.md` **하단**에 `## 테스트 시나리오` 섹션으로 추가하고, 그 아래에 승인된 AC 커버리지 대조표를 둔다. 정상, 경계, 예외 순으로 묶는다. 기록한 뒤 파일 경로를 알려 주고 끝낸다. 테스트 코드 구현은 이 스킬의 범위 밖이므로 다음 단계로 제안만 한다.
