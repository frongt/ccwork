# doc-sync-check

기능 기획 문서(`spec-fixed.md`, `prd.md`, `issues.md`) 사이의 **용어/규칙/범위 불일치**와 **`CLAUDE.md` 위배**를 찾아서 보고한다.
이 스킬은 **점검과 보고까지만** 자동으로 한다. 수정은 사용자가 승인한 항목만 한다.

## 0. 시작 조건 (가장 먼저 확인)

사용자가 `docs/features/` 아래의 **어떤 폴더를 점검할지 지정했을 때만** 점검을 시작한다.

- 폴더를 지정하지 않았다면 점검 파일을 읽거나 분석하지 않는다. `docs/features/`의 하위 폴더 목록(예: `tag`, `search`, `trash`)만 `ls`로 보여주고, **어떤 폴더를 점검할지 일반 텍스트로 먼저 묻고 멈춘다.** (선택지 대화상자 대신 사용자가 직접 답하게 한다.)
- 여러 폴더를 지정하면 폴더별로 따로 점검하고 따로 보고한다.
- 지정한 폴더가 없으면 목록을 보여주고 다시 묻는다.

## 점검 대상과 기준

| 구분                           | 파일                                 | 역할                                                                         |
| ------------------------------ | ------------------------------------ | ---------------------------------------------------------------------------- |
| 점검 대상                      | `docs/features/{폴더}/spec-fixed.md` | 확정 요구사항, 용어 정의                                                     |
| 점검 대상                      | `docs/features/{폴더}/prd.md`        | 기술 결정(ADR), Out of Scope                                                 |
| 점검 대상                      | `docs/features/{폴더}/issues.md`     | 이슈 분해, 완료조건(AC)                                                      |
| **기준 문서 (점검 대상 아님)** | `CLAUDE.md`                          | 규칙 원본. 읽기만 하고 **절대 수정하지 않으며 점검 결과 표에도 넣지 않는다** |

- 위 3개 외의 파일(`spec-original.md`, `horizon_issues.md` 등)은 점검하지 않는다. 폴더에 있다면 "점검 제외"로 한 줄만 알린다.
- 3개 중 없는 파일은 "파일 없음"으로 표시하고 나머지로 점검한다.
- 문서 간 충돌 시 기본 우선순위는 `spec-fixed.md` > `prd.md` > `issues.md`(기획 워크플로우의 산출 순서)이다. 단, 이는 **제안의 기본값일 뿐**이고 어느 쪽을 맞출지는 사용자가 결정한다.

## 1. 읽기

`CLAUDE.md`와 대상 폴더의 3개 파일을 전부 읽는다. `CLAUDE.md`가 `@`로 가져오는 문서(예: `docs/design-system/rules/do-and-dont.md`)도 CLAUDE.md 규칙의 일부로 본다. 필요하면 `src/`의 실제 파일명/식별자를 확인하되, 코드는 수정하지 않는다.

## 2. 점검 항목

### A. 문서 간 정합성 (spec-fixed ↔ prd ↔ issues)

1. **용어**: 용어 정의 표(spec-fixed, prd)의 용어가 서로 같은가. 한 용어를 다른 단어로 부르지 않는가(예: "삭제"와 "이동" 혼용). 정의된 용어를 본문/AC가 다른 의미로 쓰지 않는가.
2. **식별자**: 함수·필드·컴포넌트·파일 경로 이름(`trashNote`, `deletedAt` 등)이 문서마다 같은가.
3. **규칙/수치**: 제한값, 확인창 정책, 정렬/표시 규칙, 에러 처리, 저장 시점 등 동일 규칙이 문서마다 같은 값인가.
4. **범위**: spec-fixed에서 확정한 것이 prd Out of Scope에 들어가 있지 않은가. 반대로 Out of Scope 항목이 issues AC에 들어가 있지 않은가.
5. **이슈 ↔ 요구사항**: spec-fixed의 확정 사항이 issues AC에서 빠지지 않았는가. AC가 spec/prd에 없는 요구사항을 새로 만들지 않았는가.
6. **ADR ↔ 이슈**: prd의 Decision(계층·파일·구현 순서)과 issues의 "관통 범위"가 일치하는가.
7. **이슈 구조**: 요약 표의 번호/제목/의존이 본문과 같은가. 삭제된 이슈 번호 참조(`#6` 등)나 순환/역방향 의존이 없는가.
8. **참조 링크**: 문서 간 링크와 파일명이 실제로 존재하는가.
9. **서술 상태**: "TODO", "뼈대", "대기 중" 같은 낡은 문구나 확정 후에도 남은 미정 표현이 없는가.

### B. CLAUDE.md 위배

3개 문서가 **기획하는 내용(파일명, 구조, 규칙, UI 문구)**이 `CLAUDE.md`에 어긋나는지 본다. 예:

- 컴포넌트: named export, export명 = 파일명(`PascalCase.tsx`), props는 `XxxProps`, `useNotes()`는 최상위 조립 컴포넌트에서만.
- 분리 원칙(ADR-002): 규칙은 `utils/*.ts` 순수 함수, 상태·동작 둘 이상은 `hooks/use*.ts`, UI 조각은 순수 컴포넌트.
- 상태관리: 외부 라이브러리·reducer·memo 계열 훅 금지, `useState` + Context만.
- API 패턴: 컴포넌트가 직접 `fetch` 금지(Context 경유), 서버 응답 후 로컬 갱신, 낙관적 업데이트·refetch 없음, 수정은 `PATCH`.
- 네이밍: 파일/훅/Props 콜백(`onXxx`)/핸들러(`handleXxx`)/불리언(`isXxx`), 인터페이스·타입 파일 규칙.
- UI/스타일: 문구 한국어, 날짜 `toLocaleDateString('ko-KR')`, Tailwind 시맨틱 토큰, 디자인 시스템 Do/Don't(아이콘·이모지, 구분선, 순수 검정, `aria-label` 등).
- 커밋/문서 규칙, 테스트 방식(`useNotes`/`api` mock 또는 `NotesProvider`).

`CLAUDE.md`의 규칙이 모호하면 위배로 단정하지 말고 "확인 필요"로 표시한다. 문서가 규칙의 의도적 예외를 근거와 함께 명시했다면(예: ADR로 정당화) 위배로 보지 않는다.

## 3. 보고 형식

점검이 끝나면 **파일 단위로 표**를 만들어 보여준다. 파일마다 표 하나, `CLAUDE.md`는 표에 넣지 않는다.

```
### spec-fixed.md
| # | 구분 | 위치 | 문제 | 근거 | 수정 제안 |
| - | ---- | ---- | ---- | ---- | -------- |
| 1 | 문서 간 / CLAUDE.md | 섹션·줄 | 무엇이 어긋나는가 | 맞서는 문서·줄 또는 CLAUDE.md 항목 | 어느 파일의 어느 문구를 어떻게 바꿀지 |
```

- 문제가 없는 파일은 "이상 없음" 한 줄로 표시한다(빈 표 금지).
- `#`은 보고서 전체에서 이어지는 번호로 매겨 사용자가 "3번, 5번 수정"처럼 지목할 수 있게 한다.
- `구분`은 `문서 간` 또는 `CLAUDE.md`로 쓰고, 단정이 어려우면 `(확인 필요)`를 붙인다.
- `수정 제안`에는 **파일, 위치, 변경 전 → 변경 후**를 구체적으로 쓴다. 문서 간 충돌이면 어느 쪽에 맞추는 안인지와 이유를 적고, 반대 방향의 대안도 한 줄로 덧붙인다.
- 표 뒤에 요약(파일별 문제 수, 문서 간/CLAUDE.md 건수)과 "어떤 항목을 수정할지 알려 달라"는 한 줄만 둔다.

## 4. 승인 후 수정

- **점검 중에는 어떤 파일도 수정하지 않는다.** 승인 없이 고치지 않는다. 표를 보여주고 멈춘다.
- 사용자가 번호나 "전부"로 승인한 항목만 수정한다. 승인되지 않은 항목은 손대지 않는다. 사용자가 다른 방식을 지시하면 그대로 따른다.
- 수정 후 변경한 파일·위치와 변경 전후를 보여주고, 수정된 항목이 해소됐는지 해당 부분만 다시 확인한다.
- `CLAUDE.md`는 어떤 경우에도 수정하지 않는다. `CLAUDE.md` 쪽을 고쳐야 해결되는 문제는 "CLAUDE.md는 점검 대상이 아니므로 문서 쪽을 맞춰야 한다"고 알리고 문서 수정안만 제안한다.
- 커밋/푸시는 사용자가 요청한 경우에만 한다.

## 주의

- 코드(`src/`)와 `db.json`은 수정하지 않는다.
- 추측으로 문제를 만들지 않는다. 근거(파일과 줄)를 댈 수 없으면 보고하지 않는다.
- 이미 `git`에 커밋된 문서를 수정하는 것이므로, 수정 후 `git diff`로 변경 범위를 확인할 수 있다고 안내한다.
